## 二、四条结论

### 1. 你感觉的「崩」，一半不是崩溃

- **13 次**是机器关机/睡眠（1074/6006/42 事件可对到秒）
- **8 次**是你关窗后 host 卡死超 5 秒被强杀（`shutdown.timeout`→`run.forced-exit`）——这是 DSH 的关闭路径缺陷，下次启动照常
- 合计 21/78 不该记成事故。之前的「31 次未干净退出」有一大半是这两类。

### 2. 最大的真实故障是「点了打不开」，而且和配置无关

18 次同一个症状：

```
0.3–0.7 秒内：run.start → runtime.failed(ERR_FAILED (-2) loading 'dsh-app://app/') → shutdown.start → run.end
profile 没有任何一条 host.start.start —— 插件和配置根本没加载
```

所以「回滚备份」对它是无效的。它常在同一分钟内连发 2–3 次（10-19 04:53 三次、10-20 01:59 三次），最后一次出现在 **10-23 10:24**，此后 34 小时未复现。

### 3. 能靠备份救的只有 3 次 / 78

| 时间 | 症状 | 可修 |
|---|---|---|
| 10-17 01:22 | `Unexpected token '\ufeff' ... is not valid JSON`（UTF-8 BOM 写坏了配置） | ✓ 回滚 |
| 10-23 08:31 | `web boot: 1 entry did not activate @local/dsh-clarify-tier: import failed` | ✓ 回滚 |
| 10-23 08:33 | 同上，8.5 秒 | ✓ 回滚 |

另有 **1 次** host 进程退出（`1073807364`，10-19 23:09 那个 8.8 小时的会话），发生在机器关机前 23 秒——归因存疑，已单列。

### 4. 8 次终止没有任何证据，别猜

无 `run.end`、无 `runtime.failed`、关机也对不上（10-17 凌晨 5 次、10-19 1 次、10-23 2 次）。其中 2 次带 `child-process-gone: network.mojom.NetworkService`（reason=killed / crashed）。这类只交人工，判定器不硬猜。

## 三、不写代码也能立刻做的四件事

1. **崩了先试安全模式**，别急着改配置：
   `"D:\AI\DSH-NEXT\app\DSH NEXT.exe" --next-safe-mode`
   它用独立数据目录（`electron-user-data\safe-mode`）的临时环境，退出即回原 Profile，不动你的文件。
2. **写 JSON/YAML 不要用 `Set-Content -Encoding UTF8`**（会写 BOM，10-17 那次就是它）。用 `[IO.File]::WriteAllText` + `UTF8Encoding($false)`。
3. `@local/dsh-clarify-tier` 起不来时，**先看它自己的 import 报错**，直接回滚会把这个插件静默关掉。
4. 关窗卡死那条（8 次）值得单独报给应用方——那是关闭路径的问题，跟备份无关。
